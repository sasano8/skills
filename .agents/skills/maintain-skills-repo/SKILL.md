# maintain-skills-repo — 文書を参照してスキル群を保守する

このリポジトリ専用の作業手順。最初に [参照マップ](references/sources.md) を読み、
入口文書 A の適用範囲と現在の規約を確認する。詳細な規則・コマンドは正本の該当箇所で確認し、
このファイルの生成時点の情報だけで判断しない。

## 1. 変更の対象と既存状態を確認する

リポジトリルートで作業し、依頼が新規追加・既存スキルの変更・共通定義の変更・ガイドの整理・リリースの
どれかを特定する。作業ツリーの差分と既存の同目的スキルを確認し、利用者の変更を保持する。
参照マップ A「編集するときの注意」と B「リポジトリ構成」を読み、編集すべき正本と生成物を区別する。

## 2. 作業に必要な規則を読む

- **新規プラグイン／スキル** — B「プラグインを 1 つ追加する」と C を読み、構成・登録先・
  既存名との衝突を確認する。共通文書の要否は B「スキル間で定義を共有する（生成コピー方式）」で判断する。
- **既存の手順／共通定義** — A「編集するときの注意」と対象プラグインの README・正本を読み、
  共通部分とスキル固有の手順を分ける。配布用コピーを直接編集しない。
- **Claude／Codex 対応** — A「エージェント間の共通化」と B「Claude Code / Codex の共通仕様」
  「ベンダー固有ファイル」を読み、本体と固有設定を分ける。
- **開発ガイドの整理** — B「最初に読むもの」と F の該当節を読み、入口の README、
  編集規約 A、`docs/` 配下の開発手順 B・導入手順 F の役割を保つ。
  詳細ガイドの配置は A に従い、移動前のリンクや節名を参照しているファイルも調べる。
- **リリースを依頼された場合** — B「開発環境と普段の流れ」と D の該当ターゲットを読み、版・タグと操作範囲を確認する。
  通常の編集依頼だけでリリースや push を実行しない。

対象プラグインの文書は変更前に実際に開く。プラグイン固有の定義がどのファイルを正本とするかは
A と対象文書の明記に従い、入口から必要な節だけをたどる。

## 3. 正本を編集し、配布物の整合を確認する

読んだ規約に従って依頼範囲のファイルを編集する。新規追加では manifest・スキル本体・
エージェント別メタデータ・カタログ登録を B の手順でそろえる。
追加や改名で一覧が変わる場合は、C と照合する。

共通定義を変更した場合は B「スキル間で定義を共有する（生成コピー方式）」と D を読み直し、
そこに定めた同期コマンドをリポジトリルートで実行する。生成物の差分も確認する。

ガイドを移動・再構成した場合は、このスキルの参照マップと手順も現行文書へ照合する。
ファイルのリンクだけでなく、参照する節名・文書の役割・コマンドの選び方を確認する。
文書内の相対リンクは移動後の配置から解決し、コマンドを実行するリポジトリルートと区別する。
このスキルの生成先・名称は対象リポジトリ専用のままとし、配布プラグインの一覧へは混ぜない。

## 4. 検証して結果を返す

B「検証の中身と CI」、D の検証ターゲット、E を読んで、現在の検証コマンドを実行する。
失敗したら出力から原因を切り分ける。未実行・失敗・成功を分け、未検証の動作を成功扱いにしない。
導入方式を変更した場合は F「インストール」の該当方式を読み、必要な範囲の導入確認も行う。
ホームの設定を変更するターゲットは、その対象が依頼の範囲にあるか確認してから使う。

完了時は、変更した正本、生成物とメタデータ・登録の整合、検証結果、未解決事項を短く報告する。
リリースの場合の版更新は A と B の規則に従う。

## 正本の不足・矛盾

必須文書が見つからない、参照した節がなくなった、正本と手順・実行定義が矛盾する場合は、
該当する判断を止めて不足と影響を報告する。古い要約や推測で規則を補わない。
明記された優先関係のない矛盾は、勝手に新しい文書を優先せず確認する。
独立して進められる調査・編集・検証は続ける。
