# merge-issues — 対応方針をソースのタグへ還す

**先に同じディレクトリの [`reference.md`](reference.md) を読む。** 原則・ディレクトリ体系・config と
scope・課題票の書式・タグ文法・モード・設計の根拠はそちらが正本で、ここには書かない。

**責務は課題の転記のみ**（作業はしない）: このスキルが書くのはタグ（追跡情報）だけで、コード・
ドキュメントの中身は直さない。不一致の削除・修正といった実作業は、マージ後にタグを起点として
通常の開発作業で行う（＝このスキルの外）。

ユーザーが求めているのが**一覧だけ**なら、ここでは何も書かずに `grep-issues` へ渡す。
マージ前に現状を確認したいときも同じ（`grep-issues` が read-only の正本）。

## 手順

対応方針が決まった課題（対話回答または課題票の「対応方針」欄の記入）をソースへ還す。

1. **scope 確定** — `reference.md`「config と scope」のとおり config を読む。
2. **対象の同定** — `issue/` の open 節のうち、対応方針が記入済みのものを拾う。
3. **転記** — 採用・却下・保留のいずれも、該当ソース箇所へ `reference.md`「タグ文法」のタグとして
   マージする（コードファースト＝以後の正はソース側のタグ）。ソースに紐づかない課題（設計・横断）は、
   対象プロジェクトの然るべき記録先（設計メモ・バックログ等）へ移す。
4. **課題票のクリーンアップ** — **マージ済みの課題は節ごと削除する**（課題の中身は残さない＝正の
   二重化を避ける）。ただし**レイヤーファイル自体は空になっても削除しない**（置き場を安定させる
   ＝次回の起票先・ユーザーの記入先として残す）。
5. **残置** — 方針が決まらない課題は `open` のまま残す（次回の `extract-issues` 実行時に再提示）。

書き込みの確認粒度は `reference.md`「モード」（confirm / force）に従う。

## extract-issues との関係

このスキルは課題を**起票しない**。読解して新しい課題を見つける必要があるなら `extract-issues` を
使う。逆に、ここでマージしたタグは次回の `extract-issues` の重複判定に効く（既知の課題は再起票
されない）。
