# track-issues — 課題管理の規定と起票の入口

**先に同じディレクトリの [`reference.md`](reference.md) を読む。** 課題の管理場所（ディレクトリ体系の
`issue/`）・課題票の書式・タグ文法・タグの列挙は、**このスキルが司る規定**としてそちらに定義がある。
課題を書く・読む他のスキルや外部の仕組みは、このスキルを通じてその規定に従う。

責務は**規定の提示と、持ち込まれた課題の起票まで**。コードを読解して課題を発見するのは
`extract-issues`、対応方針をソースのタグへ還すのは `merge-issues`（このスキルは発見も転記もしない）。

## 手順

1. **宣言と scope 確定** — `reference.md`「課題管理の宣言」を確認する（規約ファイルに宣言が
   無ければ、distillation で課題管理を行うかを確認して宣言を書いてから進む）。次に「config と
   scope」のとおり config を読む。
2. **受領** — 起票したい課題を受け取る（ユーザーの対話、品質監査など外部の仕組みの持ち込み）。
   レイヤー（incompat / bug / refactor / design）を判定する。
3. **重複判定** — `reference.md`「タグの列挙（grep 仕様）」で既存タグ・open 節と突き合わせ、
   既知の課題（open・採用済み・却下・保留）は再起票せず既存の記録を示す。
4. **起票** — `reference.md`「課題票の書式」に従って `issue/<layer>.md` へ 1 課題 1 節で書く。
   持ち込み元が追跡できる根拠（file:line、監査ルール ID 等）を「根拠」に残す。
5. **提示** — 起票した課題と対応方針の記入先を示す。方針が決まったら `merge-issues` を提案する。

## 規定だけ知りたいとき

起票せず「どこに・どの書式で課題を管理しているか」を答えるだけでもよい（その場合は何も書かない）。
現状の一覧が要るなら `grep-issues`（read-only）へ渡す。
