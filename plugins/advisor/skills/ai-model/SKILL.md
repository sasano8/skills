# ai-model — 現在のモデルと速度設定を調べて助言する

**先に同じディレクトリの [`reference.md`](reference.md) を読む。** 作業場の場所・成果物の書式・
既存ファイルの扱いはそこが正本（このファイルへ再記載しない）。

Claude Code / Codex のモデル選択肢を**回答時点で検索**し、事実と推測を分けて用途別に助言する。
モデル一覧や組み合わせをこのスキルへ固定しない。結果は作業場の `<target>/ai_model.md` へ残す。

## 0. 作業場と既存の調査結果を確認する

reference.md の「置き場所の解決」に従って作業場を特定し、target を同定する。
`ai_model.md` が既にあれば**先に読み**、`researched_at` を示して次を確認する。

- 再調査する（既定。以降の手順へ進む）
- 既存のまま読むだけ（1〜5 を飛ばし、内容を要約して返す）

古い内容を黙って答えに流用しない。

## 1. 対象と優先順位を定める

ユーザーの依頼から次を拾う。不明でも調査は先に進め、推薦を左右する不足だけを調査結果の後で確認する。

- 対象: Claude Code / Codex / 両方
- 用途: 対話、実装、調査、レビュー、デバッグ、大規模設計、長時間の自律作業、大量処理など
- 優先順位: 応答速度、推論品質、コスト、利用枠、コンテキスト長
- 環境: CLI / アプリ / API、契約プラン、API・クラウドプロバイダー、組織の制限

「速度」が何を指すか曖昧なら、初回応答までの待ち時間、生成速度、タスク完了時間、reasoning/effort、
高速実行モード、コスト・利用枠を別の軸として扱う。

## 2. 公式情報を検索する

**回答ごとに Web 検索を行い、該当ページを実際に開く。検索結果の抜粋だけで確定しない。**

優先する一次情報:

- Claude Code: `code.claude.com/docs`、モデル仕様・価格は `platform.claude.com/docs`
- Codex / OpenAI: `developers.openai.com/codex`、`developers.openai.com/api/docs`、`platform.openai.com/docs`、
  Codex アプリ・ChatGPT プラン固有の情報は `learn.chatgpt.com`

各製品について最低限、次を確認する。

1. 現在選べるモデルと alias / default の解決先
2. 各モデルの公式な位置づけと、対象製品で本当に利用できるか
3. effort / reasoning effort の対応レベルと既定値
4. fast / pro / multi-agent など、effort とは別の実行モード
5. プラン、プロバイダー、クライアント版、組織設定による制約
6. 公式が示す速度・品質・コストのトレードオフ

公式情報が不足するときだけ、ベンダーのリリースノートや信頼できる測定結果を補助情報として使う。
第三者測定は一次情報と混ぜず、測定日・条件・出典を示す。ローカルで選択可能な項目と公開情報が食い違う場合は、
クライアント版・プラン・段階提供の差を疑い、ユーザーの画面や非対話の確認コマンドを優先する。

## 3. まず調査結果を提示する

推薦や結論より先に `調査結果（YYYY-MM-DD 現在）` を示す。導入文でもおすすめを先出ししない。
製品ごとに以下を簡潔にまとめ、主張の近くにリンクを置く。

- 現在のモデルと役割
- 選択できる速度・推論設定
- 有効・無効な組み合わせと提供条件
- default / alias / fallback の注意
- 公式に確認できない事項

事実には `公式確認`、資料から導いた判断には `推定` と明記する。価格、モデル階層、スループットから
実測レイテンシを断定しない。公式が速度を数値化していなければ相対評価も推定として扱う。

## 4. 用途マトリクスを作る

Claude Code と Codex を別表にし、**現在サポートされるモデル × 速度・推論設定の組み合わせ**を網羅する。
組み合わせが多い場合は、助言が同じ隣接レベルをまとめてもよいが、含めた設定名をすべて列挙する。

| モデル | 速度・推論設定 | 応答速度 | 推論品質 | コスト・利用枠 | 向く用途 | 避ける用途 |
| --- | --- | --- | --- | --- | --- | --- |

上記の列は省略しない。価格を求められていなくても、速度を上げるモードが追加課金・利用枠消費・提供条件を伴うかを
`コスト・利用枠` に記載する。

Claude の高速モードのように effort と独立した設定は別列にするか、標準/高速を別行にする。
非対応の直積は推薦表へ混ぜず、`非対応・条件付き` として注記する。同名の effort がモデル間で同じ計算量だと仮定しない。

評価は `最速 / 速い / 中間 / 遅い / 最も遅い`、`定型 / 標準 / 高度 / 最難関` など、意味のある少数段階にそろえる。
根拠が公式の定性的説明だけなら、表の評価も定性的に留める。

## 5. 推奨構成を絞る

ユーザーの優先順位順に、次の形で 1〜3 個へ絞る。

1. **既定のおすすめ** — 最も頻繁な用途に合う構成
2. **速度優先** — 品質低下が許容範囲の構成
3. **品質優先への切り替え先** — 難問や失敗コストが高い場合

各推薦に「この条件なら一段上げる／下げる」という切替条件を添える。小さいモデルへ高い effort を与える構成と、
大きいモデルを低い effort で使う構成を自動的に同等とみなさない。最高 effort や高コストモードは、測定された改善が
重要な難問に限って勧める。

最後に、公開情報だけでは決められない僅差は、代表タスクを同じ入力で 3〜5 回試し、中央値の完了時間・成功率・
手戻り回数・使用量で比較するよう提案する。

## 6. 成果物へ書き出す

3〜5 の内容を作業場の `<target>/ai_model.md` へ書く（書式・frontmatter・既存があるときの扱いは reference.md）。
`researched_at` は調査を実施した日。過去版があれば、変わった点を「前回からの変更」節に書く。

会話へは**要点と差分だけ**を返し、ファイルの全文を貼り直さない（正を二重化しない）。
最後に成果物のパスを示す。
