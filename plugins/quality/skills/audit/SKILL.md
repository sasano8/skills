# audit — 品質規約に照らして監査し、是正をタスク化する

**先に同じディレクトリの [`reference.md`](reference.md) を読む。** 品質規約（R1〜R17）・リファレンス雛形・
関心の分離・監査レポート様式はそちらが正本で、ここには書かない。

このスキルの責務は**監査と、是正の振り分け（タスク化 / 課題票への先送り）まで**。docs サイトの公開 CI は
`mkdocs`、PyPI へのリリース CI は `release-pypi` が持つ（それぞれ自分の関心の差分だけを足す）。

スキャフォルダではなく「あるべき姿との差分を埋める」運用。新規リポジトリは全項目が「不在」として挙がる
だけで同じ流れに乗る。

## 手順

1. **規約提示** — `reference.md`「品質規約（ルール）」を対象に適用することを宣言する。プロジェクト固有の
   例外があれば**ここで確認して上書きする**（例: `requires-python`、ソースレイアウト）。あとから緩めない。
2. **監査 → 問題点の列挙** — 各ルールを **OK / 違反 / 不在** で判定し、違反・不在を一覧化する。各項目に
   `ルールID / 現状 / あるべき姿 / 重大度 / 是正方針` を書く（`reference.md`「監査レポート様式」）。
3. **振り分け** — 各指摘を「即応する / 先送りする」に分ける。**即時対応するか判断に迷う・今回は
   直さない指摘は、`reference.md`「先送りする指摘の扱い」に従って受け皿（課題票）へ起票し**、
   方針決定を待つ（このスキルでは修正しない）。受け皿は対象の規約ファイル（AGENTS.md 等）の
   課題管理の宣言で解決し、**宣言が無ければ起票せず、対話で保留として列挙するに留める**。
4. **タスク化 → 処理** — 即応する是正を **`TaskCreate` でタスク登録**し、順に処理する（着手で
   `in_progress`、完了で `completed`）。粒度は **1 ルール（または 1 ファイル）単位**で、依存関係が
   あれば順序を明示する。最後に `make check`（整形確認＋fast test）が緑で完了。

**勝手に commit しない**（是正後の commit 可否はユーザーに委ねる）。既存ファイルは上書きせず、差分を
提示してから直す。

## 判定のときに間違えやすいところ

- **判断系ルール（R11 / R14 / R16）は重大度が文脈依存**。機械的に「不在＝高」と付けない。
- **対象は自リポ/統治下のみ**。外部から取り込んだスキル・依存は統治外＝規約対象外。
- **R8（`make check` 緑）は実際に走らせて判定する**。ターゲットの存在確認で代替しない。
- **R10 は技術文書側を見る**ルール。Makefile が正しくても、技術文書がベタ書きしていれば違反。
- **合意済みの却下・保留（タグ・課題票等の永続記録）は再指摘しない**（`reference.md`「先送りする
  指摘の扱い」）。挙げる場合は「合意済み例外」と明示する。

## 自走しない

このスキルは**オンデマンド監査**であって、定期実行や横断スイープを持たない。各 repo が自分の開発内ループ
（開発 → 自己点検 → commit）から呼び出すのが正路で、R10 の「検証規約の取り込み」もその repo 自身の
自己点検で確認する。

複数 repo を束ねる俯瞰層は**配下を横断監査しない** — drift が気になれば各 repo へ「自己点検せよ」と
下り dispatch するだけで、実点検はその repo 側で走る。これで俯瞰層 → 作業フロー → 品質規約が一貫する。
単発で叩きたいときはこのスキルを直接起動し、対象 repo の技術文書を R10 で監査する。

## 他言語への拡張

いまは Python のみ。他言語が要るときは `reference.md` に言語別のルール表＋雛形を足して拡張する
（**スキルは分割しない**）。
